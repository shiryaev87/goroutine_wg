# goroutine_wg
Как ускорить код на Go в 200 раз: горутины, WaitGroup и atomic на примере задачи с собеседования
Хабы: Go, Concurrency, Программирование, Карьера в IT-индустрии · Теги: golang, горутины, sync.WaitGroup, atomic, data race, собеседование

 Есть цикл из 1000 «сетевых запросов», который работает секунду. Если просто дописать go, получим две проблемы: гонку данных и преждевременный выход main. Решаем их через sync.WaitGroup и sync/atomic, получаем ~2–5 мс вместо ~1000 мс. Заодно разберём, почему не мьютекс, где здесь подводные камни и что делать, когда запросов не 1000, а миллион.

Условие задачи
Задача встречается на собеседованиях на Go-разработчика: «код работает 1 секунду, ускорьте его».

const numRequests = 1000

var count int

func networkRequest() {
    time.Sleep(time.Millisecond)
    count++
}

func main() {
    defer timer()()
    for i := 0; i < numRequests; i++ {
        networkRequest()
    }
}

func timer() func() {
    start := time.Now()
    return func() {
        fmt.Printf("count %v took %v\n", count, time.Since(start))
    }
}
networkRequest имитирует обращение к сети: ждёт 1 мс и увеличивает глобальный счётчик. main вызывает её 1000 раз подряд, а timer через defer печатает итог. Вывод будет примерно таким:

count 1000 took 1.12s
Почему так медленно
Вызовы идут последовательно: каждый следующий запрос ждёт завершения предыдущего. Время складывается: 1000 × 1 мс ≈ 1 с (на практике чуть больше, потому что Sleep никогда не спит ровно столько, сколько просили).

Важное наблюдение: большую часть времени программа ничего не делает, она просто ждёт. Это классический I/O-bound сценарий, и именно такие задачи лучше всего ложатся на конкурентность.

Первая мысль и две ловушки
Самое очевидное решение: дописать go перед вызовом.

for i := 0; i < numRequests; i++ {
    go networkRequest()
}
Код компилируется и даже запускается, но он сломан двумя способами.

1. Преждевременный выход. main не ждёт фоновые горутины. Цикл отрабатывает за доли миллисекунды, main завершается, и программа умирает вместе со всеми горутинами. timer покажет время около нуля, а count будет 0 или случайным числом.

2. Data race. Операция count++ не атомарна: это чтение, увеличение и запись. Если две горутины одновременно прочитают одно и то же значение, один инкремент потеряется. Итог окажется меньше 1000, причём каждый раз разный.

Гонку легко поймать встроенным детектором:

go run -race main.go
Он покажет WARNING: DATA RACE с указанием обеих строк, которые обращаются к count. Привычка гонять тесты и сервисы под -race экономит часы отладки.

Правильное решение
Нужно сделать две вещи: дождаться всех горутин и безопасно менять счётчик.

const numRequests = 1000

var count int64 // atomic требует int64

func networkRequest() {
    time.Sleep(time.Millisecond)
    atomic.AddInt64(&count, 1) // атомарный инкремент
}

func main() {
    defer timer()()

    var wg sync.WaitGroup
    wg.Add(numRequests) // сколько горутин ждём

    for i := 0; i < numRequests; i++ {
        go func() {
            defer wg.Done() // горутина завершилась
            networkRequest()
        }()
    }

    wg.Wait() // main ждёт все горутины
}

func timer() func() {
    start := time.Now()
    return func() {
        fmt.Printf("count %v took %v\n", atomic.LoadInt64(&count), time.Since(start))
    }
}
Результат:

count 1000 took 2.3ms
На вашей машине цифры будут другими, обычно в диапазоне 1.2–5 мс. Это ускорение примерно в 200–500 раз.

Как это работает
Параллельное ожидание
Каждая горутина стартует почти сразу и засыпает на 1 мс независимо от остальных. Планировщик Go не держит под каждую по потоку ОС, поэтому тысяча спящих горутин почти ничего не стоит. Общее время теперь равно не сумме ожиданий, а самому долгому из них, плюс небольшие накладные расходы на создание горутин.

sync.WaitGroup
WaitGroup это счётчик «сколько ещё работ не закончено»:

Add(n) увеличивает счётчик;
Done() уменьшает его на единицу;
Wait() блокирует вызывающую горутину, пока счётчик не станет нулём.

Благодаря этому main не дойдёт до конца (и до вывода из defer), пока все 1000 горутин не вызовут Done().

Здесь количество работ известно заранее, поэтому достаточно одного wg.Add(numRequests). Если количество динамическое, вызывайте wg.Add(1) в цикле перед запуском горутины, но не внутри неё. Иначе Wait() может отработать раньше, чем горутина успеет себя зарегистрировать.

for _, job := range jobs {
    wg.Add(1)
    go func() {
        defer wg.Done()
        process(job)
    }()
}
И используйте defer wg.Done(): так счётчик уменьшится даже при return по ошибке или панике внутри горутины.

sync/atomic
Чтобы убрать гонку, мы поменяли тип счётчика на int64 и заменили count++ на atomic.AddInt64(&count, 1). Это одна неделимая операция на уровне процессора (на x86 это что-то вроде LOCK XADD), поэтому потерянных инкрементов не бывает.

Чтение в timer мы тоже делаем через atomic.LoadInt64. Технически к этому моменту все горутины уже завершились, и wg.Wait() даёт нужные гарантии порядка. Но смешивать атомарные и обычные обращения к одной переменной плохая практика: потом кто-то поменяет логику, и гонка вернётся.

А что насчёт мьютекса?
Мьютекс тоже решил бы задачу, и на собеседовании такой ответ, скорее всего, приняли бы:

var (
    mu    sync.Mutex
    count int
)

func networkRequest() {
    time.Sleep(time.Millisecond)
    mu.Lock()
    count++
    mu.Unlock()
}
Но для одного целочисленного счётчика атомики лучше:

проще читаются, нет пары Lock/Unlock, которую можно забыть;
не блокируют горутины и не вызывают переключений контекста;
работают быстрее при высокой конкуренции.

Мьютекс нужен, когда надо защитить несколько связанных переменных или составную операцию. Для одной переменной он избыточен.

Современный Go: что можно сделать лучше
Начиная с Go 1.19 есть типизированные атомики, которые удобнее и безопаснее «голых» функций:

var count atomic.Int64

func networkRequest() {
    time.Sleep(time.Millisecond)
    count.Add(1)
}

// ... fmt.Println(count.Load())
Нет риска случайно обратиться к переменной без atomic, и не нужно думать про выравнивание 64-битных значений на 32-битных платформах.

Ещё одна деталь: с Go 1.22 переменная цикла создаётся заново на каждой итерации. Раньше, если замыкание использовало i или job, приходилось писать job := job. В нашем примере переменная цикла в горутине не используется, но в реальном коде это частая ловушка в старых версиях.

В новых версиях Go (1.25+) у WaitGroup появился метод Go, который сам делает Add(1), запускает горутину и вызывает Done() по её завершении:

var wg sync.WaitGroup
for i := 0; i < numRequests; i++ {
    wg.Go(networkRequest)
}
wg.Wait()
Если у вас более старая версия, используйте классический вариант выше.

Что будет, если запросов не 1000, а миллион
На собеседовании решение с 1000 горутин обычно считается правильным. Но хороший кандидат добавит: в реальной жизни запускать неограниченное число горутин опасно.

каждая горутина стартует со стеком около 2 КБ, у миллиона горутин это уже гигабайты памяти;
реальный сервис на другом конце не обязан выдерживать столько одновременных запросов;
вы упрётесь в лимиты файловых дескрипторов и сокетов.

Поэтому настоящие запросы обычно ограничивают. Самый простой способ — errgroup с лимитом:

import "golang.org/x/sync/errgroup"

g := new(errgroup.Group)
g.SetLimit(100) // не больше 100 одновременно

for i := 0; i < numRequests; i++ {
    g.Go(func() error {
        return doRequest()
    })
}
if err := g.Wait(); err != nil {
    log.Fatal(err)
}
Или классический пул воркеров: фиксированное число горутин читает задачи из канала. errgroup при этом ещё и собирает первую ошибку, чего WaitGroup не умеет.

Частые ошибки
wg.Add внутри горутины. Wait() может сработать раньше Add.
Забытый Done(). Wait() зависнет навсегда: это дедлок, Go его обнаружит и завершит программу с ошибкой.
Копирование WaitGroup. Её нужно передавать по указателю (или захватывать замыканием), копия получит свой собственный счётчик.
Смешанный доступ. Часть обращений к переменной через atomic, часть обычные: гонка остаётся.
Проверка только «на глаз». Всегда запускайте под go run -race или go test -race.

Итоги
Последовательные I/O-запросы суммируют задержки, а конкурентные ждут одновременно.
Просто go недостаточно: нужно дождаться горутин (WaitGroup) и защитить общие данные (atomic или мьютекс).
Для одного счётчика atomic проще и быстрее мьютекса.
Проверяйте код под -race и помните, что количество горутин на практике нужно ограничивать.

На собеседовании стоит проговорить не только код, но и эти нюансы: именно они отличают заученное решение от понимания.
